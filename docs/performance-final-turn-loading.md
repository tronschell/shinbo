# Hidden Agent view trace loading

Priority: P1. Opening Agent activity previously fetched and parsed the entire retained trace library, although Activity, Worktrees, and Bench do not display the parsed turns. A supported 64-thread library made 64 requests and moved about 284 MiB of trace JSON into the renderer merely to display Activity. Parsing also triggered turn statistics and friction calculations for hidden Self improvement content.

`AgentView` initializes its tab to `activity`. Its only `useTurns` call was unconditional. The Activity child receives snapshot summaries; Worktrees receives no turns; Bench receives snapshot, trial store, and selection props. All turn-dependent controls and evidence are inside the `tab === "improvement"` fragment. No model or provider request is needed to reproduce this issue.

`desktop/src/AgentView.tsx` now enables the trace-loading effect only for Self improvement. Leaving that tab invalidates the current read. Each pending response checks its lifetime before parsing, and the outer loop stops before another four-request batch. Completed data remains available across enabled renders; leaving Self improvement releases it through the tab-change event. Readiness belongs to the current enabled/signature request identity: entering again or changing the history signature cannot present stale readiness while the fresh load is pending. The original thread ordering, bench exclusion, four-request concurrency, error handling, trace normalization, duplicate ordering, and 90-day filtering remain in place.

## Actual-source comparison

Baseline snapshot: `/tmp/shinbo-native-subagent-fixture/AgentView-before.tsx`.

```sh
TURN_LOADING_BASELINE=/tmp/shinbo-native-subagent-fixture/AgentView-before.tsx node --test desktop/test/turn-loading-performance.test.mjs
```

The test extracts and transpiles the real `useTurns` declaration from each source. The request-count fixture contains 64 histories with eight traces each. Each history's JSON response is 4,652,481 bytes, below the existing 8 MiB response bound, and every trace is below 1 MiB. These traces are generated by production `encodeSpans`: one agent and 36 tool calls carrying 16,000-character outputs. Large-fixture parsing is a counted stub to isolate loading work without running a CPU benchmark during another agent's timing lane; the counts describe requested response bytes and parser invocations, not measured runtime or physical disk reads. A separate small enabled fixture uses production `readTurns` and `distinctTurns` and compares complete baseline/current output.

| Opening a hidden-turn tab | Before | After |
| --- | ---: | ---: |
| Trace history requests | 64 | 0 |
| JSON response bytes | 297,758,784 | 0 |
| `readTurns` invocations | 512 | 0 |

Entering Self improvement still performs the full 64-request, 512-trace read. This fix removes work from tabs that do not use it; it does not claim that reading the entire library on Self improvement is now cheap.

The focused tests also verify cleanup while four requests are unresolved, no parsing or further batches after leaving, fresh readiness on reentry and changed history, no parsing after unmount, failed-read behavior, bench exclusion, and exact enabled ordering/results. All three tests passed. Focused ESLint passed. The parent agent owns the full desktop checks and native Activity/Self improvement tab exercise.

## Limits

Already dispatched host requests cannot be cancelled by this renderer effect. Their responses are ignored before trace parsing. The earlier idea of filtering old traces before parsing remains deferred because doing so can change duplicate-turn ordering; this change preserves that ordering.

## Production Electron verification

A read-count-only wrapper around the actual `shinbo:thread-traces` IPC handler recorded calls and returned trace-text bytes. The baseline app made two startup reads, then 4,119 additional reads when Agent activity opened. Adding the separate local trace fixture while Activity remained visible triggered another 4,120 reads. The fixed production app began with 4,120 histories and made two selected-thread startup reads; Activity, Worktrees and Bench each left that count unchanged. Selecting Self improvement then made the expected 4,120 history reads. It displayed 4,103 total runs, including exactly 4,096 successful `local/fixture` turns. Counter snapshots are saved in `performance-native-trace-phases.json`. This is a native IPC operation-count check, not a timing comparison; initial selected-thread contents and the one added fixture differ between sessions.

## Integration: release completed evidence on departure

The first gating change stopped new hidden reads but still retained completed `Turn[]` in `useTurns`. Each turn owns parsed spans and context, and the derived `dated`, `windowed`, and friction memo values refer to that history. No other Agent tab consumes those turns: Bench decisions use persisted improvements and the proposal queue, Activity uses the snapshot, and Worktrees has no turn input. Reentry already refetches the histories and marks readiness false.

`pickTab` now clears completed turns when leaving Self improvement for Activity, Bench, or Worktrees, in the existing click event. Selecting Self improvement while already there does not clear or reread. Enabled history-signature refreshes keep their existing behavior. No effect scheduling workaround or separate cache was added. Drafts, filters, queued proposals, trial state, and the evidence first-open latch remain intact. This closes retention in the same hidden-loading fix; it is not another counted issue.

Exact integration baseline: `/tmp/shinbo-perf-turn-retention/AgentView.before.tsx`. The actual-hook test also extracts the real tab JSX and `pickTab` handler, then clicks each destination. Its supported history contains eight production-encoded traces, 4,780,657 JSON response bytes in total, with every trace below 1 MiB and the response below 8 MiB. Production `readTurns` produces eight turns, 296 spans, and 128,000 system-prompt characters. After departure the baseline hook still returns those eight turns and all their spans/context; the corrected hook returns zero of each. These are reachable values in completed hook state, not a renderer heap snapshot, GC result, or RSS measurement.

The same test checks that staying on the tab retains the identical array without a second request, reentry starts a fresh request with readiness false, and completion returns the exact original ordered data. Existing cancellation, signature/readiness, ordering, failed-read and bench-exclusion tests remain passing, as do both evidence-latch tests. Renderer typecheck and focused ESLint passed. The raw ownership comparison is in `/tmp/shinbo-perf-turn-retention/verification.txt`.

Already issued IPC requests still settle normally and their inactive responses are ignored before parsing. An explicitly started Analyze or Write action can legitimately retain its captured evidence until that requested action finishes; tab navigation does not cancel the user's action. React may retain prior render data internally until later reclamation, so this change does not promise immediate physical memory return.

The final production build also exercised the completed-history release path. Self improvement showed 4,104 turns after the separate CLI test added one run. Switching to Activity and back immediately showed Every model 0 turns, “Reading traces…”, and a disabled Analyze button while the new collection was pending. Independent review confirmed all four tab controls route through the release callback, stale requests cannot publish after effect cleanup, and active analysis actions retain their original captured intent.
