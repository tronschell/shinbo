# Independent subscription history review

Compared `desktop/src/model-plans.tsx` with `/tmp/shinbo-perf-model-plans/model-plans.before.tsx`, the implementation report in `docs/performance-model-plan-history.md`, the dedicated regression tests, `planSpend` in `desktop/shared/settings.ts`, and the Rust summary projection and snapshot filtering. No concrete correctness regression was found. No production source or tests were changed.

The candidate filter skips a thread only when every available message timestamp is strictly before collection start minus seven days. Rust builds `messageDates` from every message, independently of role, generation metadata, thread creation date, and message ordering. Exact seven-day timestamps remain candidates; exact five-hour timestamps are necessarily candidates too. The unchanged `planSpend` uses a strict less-than exclusion, so both boundaries remain inclusive. Future timestamps retain the prior behavior.

Missing date arrays and unparseable date strings conservatively request the body. An empty date array represents a known empty thread in the current host projection and can be skipped. Invalid generation timestamps remain excluded by `planSpend` after fetching; the filter does not turn them into valid spending.

The normal path measures completion once. If completion advances, the start-time filter is conservative because the eligible window can only shrink. If completion precedes collection start, a complete snapshot supplies any newly eligible older records, with its own completion timestamp. Intermediate backward movement that has recovered by completion cannot make an excluded old record eligible at the final cutoff. A further backward movement while fetching the fallback also remains safe because that fallback includes complete histories.

The helper returns only after all required reads succeed. Summary errors, selected-thread read errors, and fallback snapshot errors reject instead of publishing a partially assembled ledger. The component retains its existing initial empty state and silent read-error behavior. There is still no explicit loading/error presentation for this ledger; that is unchanged from the baseline. A record deleted after the summary read can now cause the collection to reject. These multiple reads are not a transactional snapshot, as documented; the previous full snapshot was also not transactional against concurrent file changes.

The collection stores model names and generation counts rather than resolved provider identities. Both spending memos depend on current `settings.providers`; selected-provider highlighting resolves current `settings.selectedModel` and the current provider list during render. The optimization introduces no stale provider closure or missing provider dependency. Collection remains mount-time, matching the baseline rather than adding live spending updates.

Both Rust listing paths apply the same archive retention and parser behavior. All-recent libraries still request every body and add sequential per-thread request overhead after the summary request. This is a real workload limitation, not a demonstrated speedup for that case. No new concurrency framework or all-recent heuristic is warranted by the supplied evidence.

Validation here was source-only, as requested while the parent restarted the checked app. The seven new history tests and eighteen existing provider tests were inspected; their reported prior passing runs were not repeated. No native UI, external services, or new benchmarks were invoked.
